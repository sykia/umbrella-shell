# Эксперимент: перемещение оригинальной кнопки Task View

Ручной developer-режим существующих `UmbrellaTaskbarHost`/`UmbrellaTaskbarModule`.
Он выключен в обычном GUI и `--serve`, не сохраняет раскладку и не меняет INI,
реестр, feature cache или системные файлы. Только одна кнопка основного монитора.

## Запуск и управление

Закрыть действующий сеанс оформления Umbrella. Из каталога одной и той же сборки:

```powershell
./UmbrellaTaskbarHost.exe --inspect-taskview
./UmbrellaTaskbarHost.exe --edit-taskview --seconds 120
```

`--verify-taskview` — отдельный явно запускаемый интерактивный тест: настоящие
SendInput mouse events, UIA hit-test/RECT, native Click, системная поверхность,
Esc, фокус и reset. Он перемещает курсор и временно активирует Task View.
`--verify-taskview-owner-death` оставляет успешно сдвинутую кнопку для внешнего
наблюдателя, который завершает **только этот новый host**; timeout остаётся
включённым. Это тестовые команды, не автоматические проверки при запуске GUI.

Готовый явный тестовый запуск (указать путь к своей собранной паре host/DLL):

```powershell
./scripts/Test-TaskbarButtonEdit.ps1 -HostPath ./build/windows-msvc/Release/UmbrellaTaskbarHost.exe
./scripts/Test-TaskbarButtonEdit.ps1 -HostPath ./build/windows-msvc/Release/UmbrellaTaskbarHost.exe -OwnerDeath
```

Второй вариант самостоятельно создаёт и завершает только свой новый дочерний
host, сравнивая исходную/восстановленную позицию и свойства ввода. До ввода
тест проверяет попадание в Taskbar и отказывается кликать сквозь другое окно;
при уже нажатой кнопке мыши также отказывает. Он временно запрашивает штатный
фокус Taskbar; по завершении возвращает курсор и пытается вернуть прежнее
foreground-окно. Проверки не следует запускать одновременно с ручной работой мышью.

Нужен интерактивный stdin: EOF немедленно завершает режим и запрашивает откат.
Во время второй команды захватить Task View **левой** кнопкой мыши и переместить
в свободное место вдоль панели; отпустить. Для штатного клика сначала дать
команду `preview`: она возвращает исходный hit-test, оставляя новое положение.
В консоли доступны `status`, `preview` (запретить новые захваты, оставив позицию),
`edit` (сбросить и заново включить), `reset` (снять изменение и обработчики), `quit`.
Через заданные 1–120 секунд host заканчивает сеанс с откатом.

Режим отказывает при занятой native-сессии, неподдерживаемых DLL, изменённой
геометрии/обрезке, autohide, другом DPI. Первая граница: нижняя основная панель
полной ширины, высота 48 px, 96 DPI. Второй монитор не подключается.

## Механизм и реальные родители

Читающий `--inspect-taskview` 19.10.2026 на этой машине подтвердил:

```text
Taskbar.ExperienceToggleButton  Name=LaunchListButton  AutomationId=TaskViewButton
  ← Microsoft.UI.Xaml.Controls.ItemsRepeater  Name=TaskbarFrameRepeater
  ← Windows.UI.Xaml.Controls.Grid  Name=RootGrid
  ← Taskbar.TaskbarFrame  Name=TaskbarFrame
```

Кнопка — непосредственный visual child repeater; размер 44×48 DIP, parent 2560×48.
Начальная координата относительно parent в этом сеансе: x=1239, y=0.
Это новый факт visual tree, не вывод из UIA-проекции. Смешанные runtime names
не помешали получению Windows.UI.Xaml interfaces в текущей сборке.

Используется XAML `UIElement.Translation` исходного элемента: сохраняется
исходный float3, изменяется только X; RenderTransform не заменяется. Штатный объект,
родитель, ButtonBase и обработчики Explorer не заменяются. Pointer events и
CapturePointer обрабатываются на существующем XAML-корне на его UI-потоке;
координаты берутся в parent. В режиме редактирования только перемещаемому
элементу временно задаётся IsHitTestVisible=false (с сохранением local value).
Именно существующий `RootGrid` с существующим Background захватывает левый drag
по фактическому RECT этого элемента; при отсутствии такого фона режим отказывает.
Новое окно, visual, overlay и фон не создаются. Это не
копия/overlay: рисуется и смещается исходная кнопка. В `preview` исходный
IsHitTestVisible восстанавливается, и ввод снова получает оригинальный контрол
по его новому местоположению. Его handlers не удаляются и не заменяются.

Перед первым изменением сохранён исходный float3 Translation; при native
TranslationTransition режим отказывает, чтобы не смешивать владельцев анимации.
Смещение ограничено
шириной parent. При отпускании поверх соседа возвращается предыдущее смещение:
соседи не перестраиваются, исходный layout slot остаётся на месте. Это прототип
позиционирования одного объекта, не логического reorder коллекции.

## Восстановление

- `reset`, EOF, timeout и штатный выход снимают handlers/capture и возвращают
  исходный float3 Translation и local value IsHitTestVisible/ClearValue.
- Существующий worker native-модуля следит за handle процесса host. Его смерть
  отправляет restore на UI-поток; редактирование снимается до общей очистки.
- Unloaded отменяет изменение. LayoutUpdated проверяет родителя, границы и
  пересечения после перестройки; повторного опроса по таймеру нет.
- Перед восстановлением проверяется, что Translation по-прежнему равен
  записанному экспериментом значению; более новое значение другого владельца
  не перезаписывается. Совместная работа двух модификаторов не поддерживается.
- При ошибке восстановления/отписки callbacks становятся неактивными, DLL
  закрепляется в Explorer, чтобы не выгрузить выполняемый или подписанный код.
  Ошибка возвращается вызывающему коду; это не подтверждение успешного отката.

Гарантия ограничена отзывчивым UI-потоком Explorer. Зависание Explorer, сбой
самого Explorer/ОС и потеря питания не покрываются автоматическим возвратом
живых объектов; постоянного изменения раскладки на диске нет. Существующие
worker/journal механизмы не отключены. Новый режим не вызывает native acquire
и не включает оформление/автоскрытие.

## Проверки и пределы

Host и DLL собирались точечно MSVC 14.42 / C++20 / Windows SDK 10.0.26100,
статическая CRT; без полной Qt/CMake-сборки и без установки. Результаты на этой
машине 19.10.2026:

| Проверка | Фактический результат |
|---|---|
| Читающий visual tree и EOF без перемещения | Успех; цепочка выше, обработчики снимаются |
| Реальный левый drag финального пути | Финальный прогон: 20 изменений X, та же кнопка с x=1239 в x=250, y=1392, размер 44×48 px; после отпускания остаётся на месте, Click во время drag=0 |
| Область ввода | UIA ElementFromPoint/CompareElements находят исходный элемент в новом месте, в старом — нет |
| Оригинальный левый клик | Счётчик исходного ButtonBase.Click вырос с 0 до 1; foreground — XamlExplorerHostIslandWindow, системная Task View |
| Закрытие и фокус | Esc закрывает поверхность; UIA SetFocus=S_OK, HasKeyboardFocus=true |
| Штатный reset/выход | Исходный UIA RECT восстановлен полностью; host exit=0 |
| Смерть host после drag | Тестовый дочерний host завершён при оставленном edit-режиме и сдвиге; через 1,5 с inspect показал x=1239, offset=0, IsHitTestVisible=true и прежнее наличие Background; Explorer с тем же PID |

Первый вариант RenderTransform не прошёл тест отпускания. Затем на Translation
выявлено, что штатный ButtonBase освобождает capture до нашего PointerReleased:
общий cancel-handler ошибочно возвращал исходное положение. PointerCaptureLost
теперь отличает физический button-up от отмены. Поэтому ранние неудачи не
являются доказательством принципиальной невозможности RenderTransform.

Вариант с правым drag через handlers самой кнопки прошёл один полный прогон,
но повторная серия выявила активацию Click ещё до проверочного левого клика;
другой прогон не захватил ввод. Его стабильность не подтверждена. Поэтому
финальный путь отделяет редакторский ввод на существующем XAML-корне от
штатного ввода кнопки и проверяет его после `preview`.

Первая попытка обработки на XamlRoot.Content не получила drag в пустой области;
проверенный непосредственный RootGrid оказался подходящей точкой ввода. В
проверке фокуса потребовалось дождаться закрытия Task View и штатно активировать
Taskbar: немедленный SetFocus мог вернуть S_OK до подтверждённого HasKeyboardFocus.

Раннее ручное наблюдение перетаскивания значков приложений не засчитывается:
подтверждённый результат выше получен именно для TaskViewButton нативным тестом.
Проверка основана на фактическом вводе, геометрии и событиях, а не отправке
искусственных XAML drag-событий или создании копии кнопки.

Не проверены длительная стабильность, все способы отмены drag, исчерпывающие
keyboard/touch/hover-сценарии, другие позиции/DPI/topology/версии и клики по
другим системным кнопкам. Отдельная полнота аварийных гарантий не заявляется.
Для остальных кнопок остаются модель коллекции, popup-якоря, animations, clipping
и реальные границы контейнеров, описанные в [оценке](TASKBAR_REORDER_FEASIBILITY.md).

Механизм Translation: [Microsoft API reference](https://learn.microsoft.com/en-us/uwp/api/windows.ui.xaml.uielement.translation?view=winrt-22621).
Наличие API само по себе не подтверждает совместимость с другой Taskbar.
