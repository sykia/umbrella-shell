# Перестановка оригинальных компонентов Taskbar: оценка реализуемости

Дата анализа: 19 октября 2026. База — [готовый каталог](TASKBAR_CONTROLS_INVENTORY.md), исходники проекта и первичные источники ниже. Нового обхода рабочего стола, подключения к Explorer, перемещений, сборок или GUI-тестов не выполнялось. Документ описывает исследовательскую возможность, а не реализованную функцию.

`--inspect-components` с фактическими visual parents и консервативным реестром ролей.
Это не новый desktop-обход: команда на Explorer в параллельной сессии не запускалась.
Task-list instances не имеют persistent AppID в этом снимке; Quick Settings остаётся
общей группой. Неподтверждённые контейнеры не получают разрешения на перенос.
Состояние реализации и продолжение описаны в [конструкторе](TASKBAR_CONFIGURATION.md).

применимость собственного Layout к частной Taskbar-логике всё ещё требуют проверки.

## Вывод и границы доказательств

**Свободное размещение всех компонентов с сохранением всех функций пока не доказано.** Среди изученных публичных API не найден интерфейс, который задаёт произвольные координаты и родителей всех штатных кнопок Windows 11. Наиболее перспективен доступ к настоящим XAML-объектам на их UI-потоке с изменением размещения **без смены владельца и родителя**, начиная с целых функциональных групп. Перестановка внутри управляемых коллекций потребует отдельного согласования с моделью Explorer.

Различаются четыре результата:

- **Координаты:** исходный объект отображается в другом месте. RenderTransform исходной кнопки отвечает требованию оригинальности, но сам по себе не меняет раскладку соседей.
- **Визуальный порядок:** кнопки поменялись местами на экране; порядок коллекции, клавиатурной навигации и доступности мог остаться прежним.
- **Логический порядок:** изменились последовательность элементов и согласованное с ней поведение Explorer.
- **Перенос:** исходный элемент сменил visual parent/контейнер; это отдельная, существенно более сложная операция.

Обозначения в таблице: **П** — техническая гипотеза на основании механизма XAML, на этой Taskbar не проверена; **О** — ограниченная штатная возможность; **?** — данных недостаточно. Ни одна отметка П не обещает «любую позицию»: остаются границы окна, clipping, пересечения, системные жесты и владение.

Общие свойства XAML подтверждены документацией, но их применимость к закрытым классам Explorer не следует автоматически. Каталог не проверял TransformPattern/CanMove; отсутствие доступного перемещения через UIA не измерялось. UIA parent не является доказательством конкретного visual parent.

Здесь перетаскивание не выполнялось.

Скрытый `SystemTray_Main` с battery-name — служебный объект, **не обнаруженная функциональная кнопка батареи**. Его перемещение не решает размещение батареи. Условные battery/pen/touch/notification и другие отсутствующие кнопки из каталога не получают оценку как реально существующие: для них неизвестны экземпляры, visual parent и функциональные связи.

Иконки, текст, ProgressIndicator и OverlayIcon перемещать вместе с владельцем. Самостоятельное перемещение такого потомка не переносит целиком интерактивный компонент. Фон/обводки и служебные HWND — инфраструктура, а не дополнительные пользовательские функции.

## Контейнеры и зависимости

```text
На каждом мониторе: свой Shell_*TrayWnd
  └─ DesktopWindowContentBridge / InputSite
       ├─ TaskbarFrame → R → Widgets / Start / Search / TaskView / task-list peers
       └─ system-tray peers (UIA проекция; visual родители неизвестны)
                       ↕ системные модели и отдельные popup/окна
```

1. **Общий корень не равен свободной плоскости.** Общий R в UIA показывает связь кнопок, но не раскрывает layout-класс, вложенные presenters, коллекции и ограничения. Имя Repeater само по себе не доказывает стандартный ItemsRepeater. Если используется переработка контейнеров, сохранённая ссылка на кнопку может впоследствии представлять другой элемент. Такое поведение коллекций описано для [ItemsRepeater](https://learn.microsoft.com/en-us/windows/apps/develop/ui/controls/items-repeater), но для данного R ещё не установлено.
2. **SystemTray — самостоятельная зона ответственности.** UIA-кнопки лежат под InputSite; нельзя из этого заключать, что это независимые соседи в visual tree. `SystemTray.SystemTrayFrame` известен из кода, но его потомки и реальные группировки не измерены. Сеть и громкость имеют разные peers, что не доказывает независимые layout slots или независимые flyout.
3. **Legacy HWND не являются ручками современных кнопок.** `Start`, `TrayDummySearchControl`, `TrayNotifyWnd`, `ReBarWindow32`, `MSTask*`, `WorkerW` нельзя использовать как доказанный способ перемещения соответствующей видимой XAML-функции. Уже каталог показывает несовпадение геометрии и родительства. Сдвиг bridge/InputSite затрагивал бы область сразу, а не отдельный peer.
4. **Мониторы — разные экземпляры и корни.** Совпадение AppID/AutomationId на P/S не означает общий объект. На S нет шести системных кнопок P, кроме часов; перенос одной кнопки P в S не создаёт автоматически требуемую monitor-specific модель. Смена XamlRoot/потока/хоста не эквивалентна перестановке внутри одного родителя.
5. **Всплывающие окна живут отдельно.** Start/Search/Widgets, Quick Settings, input switcher, календарь, jump lists, previews и overflow нельзя считать дочерними визуалами кнопки. Они могут использовать преобразованные координаты, исходный layout slot, сохранённый RECT, край или монитор панели. Какой путь выбран каждым компонентом этой версии, неизвестно.

## Возможные механизмы

### 1. Публичные Shell API, Win32 и UI Automation

`SetWindowPos`/`MoveWindow` задают геометрию HWND, но отдельные современные кнопки не обнаружены как самостоятельные HWND. `SetParent` меняет родителя **окна**, а не XAML-кнопки; дополнительно имеет ограничения DPI awareness. Он не переносит task-list model или XAML input root. См. [SetParent](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setparent).

`ITaskbarList` управляет добавлением/удалением и активацией элементов. `ITaskbarList3::SetTabOrder` упорядочивает thumbnails зарегистрированных вкладок **внутри группы приложения**, а не произвольные кнопки панели. Эти API не следует выдавать за интерфейс конструктора. См. [ITaskbarList](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nn-shobjidl_core-itaskbarlist), [SetTabOrder](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-itaskbarlist3-settaborder).

UIA TransformPattern работает лишь там, где провайдер его реализует и разрешает движение; наличие RECT/AutomationId не даёт записи координат. Даже CanMove не обещает свободу от ограничений контейнера. Это средство доступности, а не универсальный редактор visual tree. Поддержка паттерна этими кнопками неизвестна. См. [ITransformProvider](https://learn.microsoft.com/en-us/windows/desktop/api/uiautomationcore/nn-uiautomationcore-itransformprovider).

### 2. Свойства исходного XAML-элемента без смены родителя

Два разных пути:

- **Layout:** Margin/Alignment и, только при соответствующем родителе, Grid.Row/Column или Canvas.Left/Top. Свойство Canvas.Left не делает произвольный repeater Canvas. Arrange зависит от родителя; следующий layout pass может вернуть штатное размещение. Общие правила: [XAML layouts](https://learn.microsoft.com/en-us/windows/apps/develop/ui/layouts-with-xaml).
- **Post-layout:** TranslateTransform/RenderTransform исходной кнопки или целой группы. Сохраняется объект, шаблон и существующие обработчики; освобождение исходного места и размещение соседей автоматически не обеспечиваются. Нужно отдельно согласовать визуальный, клавиатурный и UIA-порядок. RenderTransform может конфликтовать с theme animations. См. [RenderTransform](https://learn.microsoft.com/en-us/uwp/api/windows.ui.xaml.uielement.rendertransform?view=winrt-22621).

Работа должна выполняться на владеющем UI-потоке с действительными объектами соответствующего XAML runtime. Обычное внешнее получение HWND/UIA не предоставляет такие ссылки. Наиболее осторожная гипотеза — сначала сдвиг целой исходной группы внутри прежнего корня. У отдельной кнопки потенциально сохраняются object-level события; сохранение маршрутизации, hit-test, clipping, focus и popup anchoring всё равно требует проверки. Нельзя обещать функциональность лишь по изменившемуся изображению.

### 3. Изменение коллекции/модели и reparenting

Если visual parent действительно предоставляет изменяемую коллекцию детей, теоретически можно удалить и вставить **тот же объект** по другому индексу или в совместимый существующий контейнер. Но managed items-control может владеть детьми через ItemsSource/template/layout. Прямое редактирование visual children не обязано изменять его модель и может быть отвергнуто или отменено.

Перенос также меняет наследуемые ресурсы/DataContext, цепочку routed events, focus navigation, координатные преобразования и привязку к XamlRoot. Сохранение прямого обработчика объекта недостаточно, если логика находится у старого родителя. Общий механизм событий: [routed events](https://learn.microsoft.com/en-us/windows/uwp/xaml-platform/events-and-routed-events-overview).

Настоящий логический порядок task-list, вероятно, потребует изменения модели Explorer либо её layout-политики. В изученном проекте интерфейс такой модели не найден; адреса и сигнатуры не установлены. Это направление исследования закрытого ABI, а не готовое решение. Между мониторами риск выше; перенос T↔R также пока неизвестен. Предпочтение сохранению родителя не означает доказанную невозможность reparenting.

### 4. Windows Composition / DirectComposition

`ElementCompositionPreview.GetElementVisual` даёт backing Visual **исходного** XAML-элемента. Composition translation может сдвигать его после layout; некоторые свойства Visual разделяются с XAML, поэтому запись Offset/Size способна конфликтовать с владельцем. Документированы interop и translation: [ElementCompositionPreview](https://learn.microsoft.com/en-us/uwp/api/windows.ui.xaml.hosting.elementcompositionpreview?view=winrt-26100), [Microsoft: XAML/Visual interop](https://blogs.windows.com/windowsdeveloper/2016/08/26/interop-between-xaml-and-the-visual-layer/).

Это возможная альтернатива XAML-transform для движения исходного объекта, но не готовая перестановка layout slots/коллекций. Получить visual другого процесса по одному HWND и свободно редактировать внутренние visuals нельзя считать доступным публичным контрактом. Перестройка backing visual tree вручную особенно рискованна: им управляет XAML, а visual-only порядок не определяет модель ввода/доступности.

Обычный внешний DirectComposition target, screenshot/thumbnail/surface или отдельное overlay-окно не решает требование настоящего переноса компонентов с их поведением и здесь не рассматривается как результат.

### 5. XAML Diagnostics и частные точки Explorer

Документированный диагностический `IVisualTreeService` имеет SetProperty, AddChild/RemoveChild и подписку на изменения. Это технический механизм доступа к дереву, **не контракт кастомизации Taskbar** и не разрешение обходить владельца коллекции. См. [IVisualTreeService](https://learn.microsoft.com/en-us/windows/win32/api/xamlom/nn-xamlom-ivisualtreeservice).

Первичный пример внешнего проекта — [исходник Windows 11 Taskbar Styler](https://github.com/ramensoftware/windhawk-mods/blob/main/mods/windows-11-taskbar-styler.wh.cpp): используются IXamlDiagnostics, VisualTreeWatcher и InitializeXamlDiagnosticsEx, есть логика подключения/хуков. Это свидетельство практического доступа к настоящим объектам и их свойствам, **не доказательство** свободной перестановки всех строк таблицы и совместимости с этой системой. В исследовании код не запускался и зависимости не добавлялись. Просмотренная ветка main изменяема; для реализации понадобилась бы фиксация версии и отдельная проверка.

Альтернатива диагностическому пути — существующий в Umbrella доступ через проверяемые частные точки Taskbar.dll. Оба варианта в будущем предполагают внутрипроцессную работу; запрет внедрения и хуков соблюдён сейчас. Если такой запрет станет постоянным требованием реализации, изученные внешние API не дают основания обещать универсальный конструктор.

## Сравнение подходов

| Подход | Оригинальный компонент | Свобода / согласование | Главный предел | Оценка |
|---|---|---|---|---|
| Штатное упорядочивание приложений | Да | Ограниченная область приложений | Нет универсальных координат и системных кнопок | Подтверждённая узкая функция Windows |
| Win32 над служебными HWND | Окно да, конкретная XAML-кнопка — не установлено | Группа/окно | Не та гранулярность, Explorer управляет layout | Не основа конструктора кнопок |
| UIA Transform | Только если поддержан провайдером | Неизвестно | Нет доказательств поддержки | Не рассчитывать как основной путь |
| XAML layout/transform без reparenting | Да | Потенциально координаты; логический порядок отдельно | Layout, clipping, input и flyout | Наиболее перспективный первый кандидат |
| Composition translation backing Visual | Да при работе с исходным Visual | Post-layout; модель отдельно | Конфликт с XAML, согласование ввода/якорей | Дополнительный кандидат |
| Модель/коллекция Explorer | Да | Потенциально согласованный порядок | Закрытый ABI и жизненный цикл | Нужно для полноценной семантики порядка |
| Reparenting между R/T/мониторами | Теоретически тот же объект | Возможность не установлена | Владение, runtime/root, ресурсы, модель | Самое неопределённое направление |

Механизм **получения доступа** (Diagnostics/частный ABI) и механизм **размещения** (layout/transform/модель) — разные решения; первый сам по себе не обеспечивает второй.

## Ограничения совместимости

- Каталог относится к заявленной ОС 26300.9711 и Explorer 10.0.26100.8875. Объяснение расхождения версий неизвестно. Строка 26H2 или версия explorer.exe недостаточна: важны конкретные Taskbar.dll, Taskbar.View.dll, SystemTray.dll и XAML runtime, их идентичность и активные варианты функций.
- В проекте есть проверка точных RSDS и частных RVA; обновления могут менять ABI, selectors, шаблоны, grouping и способ открытия flyout. Нельзя переносить выводы старой Win32 taskbar или другой Windows 11 автоматически.
- Пространства Windows.UI.Xaml и Microsoft.UI.Xaml не взаимозаменяемы. Смешанные имена в UIA не доказывают runtime каждого объекта; типы, interfaces и thread ownership нужно установить до будущей записи.
- Настройки поиска, badges, группировка приложений, переполнение, RTL, touch и условные tray-кнопки меняют размеры/состав. Идентичность надо отличать от временного индекса и повторяющегося SystemTrayIcon.
- Теперь известны только две горизонтальные панели при 96 DPI. Произвольные координаты должны оставаться допустимы при другом DPI, отрицательных координатах, смене основного монитора, autohide и перестройке дерева. Возможности боковой общей раскладки из проекта не доказывают такую свободу для каждой кнопки.
- Островковые HRGN/Composition clip Umbrella могут отсечь сдвинутую кнопку или область ввода. Конструктор должен был бы согласовывать их с фактической геометрией; сейчас это не реализовывалось.

## Что проверить только на следующем, отдельно разрешённом этапе

1. Установить точные runtime-типы, visual parents, layout-классы, XamlRoot/UI-потоки и коллекции R/T; определить, где владельцем выступает модель и какие объекты перерабатываются. Сначала минимальное чтение, без перестановки.
2. На ограниченной матрице DLL проверить доступ к исходным объектам и отказ на неизвестной версии. Не подменять fail-closed подбором похожих RVA.
3. После отдельного разрешения сравнить сдвиг целой группы и одной кнопки **в прежнем родителе**: XAML layout, RenderTransform, Composition translation. Проверять настоящий hit-test/UIA RECT, а не только изображение; учитывать press animations и следующий layout pass.
4. Для каждой строки матрицы проверить обычный/правый/средний клик по применимости, hover/touch, wheel, клавиатуру/Win+номер, фокус, Screen Reader и routed events. Не считать invoke успехом всей функциональности.
5. Измерить якоря, монитор, clipping, закрытие и фокус всех относящихся popup: Start/Search/Widgets, Task View, Quick Settings, язык/IME, календарь/уведомления, overflow, previews/jump lists. Текущий helper overflow не покрывает этот список.
6. Разделить визуальный обмен местами и настоящий порядок модели. Проверить запуск/закрытие/группировку окон, pinned/running, overlays/progress, drag-and-drop, переход в overflow и восстановление контейнера после recycle.
7. Только после устойчивого размещения в исходном родителе оценивать отдельные границы R↔T и P↔S; отсутствие результата не компенсировать визуальной копией или дублированием обработчика.
8. Проверить восстановление исходных свойств/порядка при штатном выходе, уничтожении элемента, перестройке Explorer и сбое управляющего процесса; не возвращать устаревший local value поверх нового состояния Windows. Замерить CPU, память, задержки и число callbacks, без постоянного polling.

**Установлено:** обнаруженные кнопки преимущественно XAML; Win32/UIA не дают подтверждённого универсального управления ими; в Umbrella уже есть ограниченный доступ к исходным XAML-объектам. **Потенциально реализуемо:** перемещение групп и отдельных оригинальных контролов внутри прежнего дерева. **Неизвестно:** полное сохранение функций при таком сдвиге, согласованный произвольный порядок и допустимость переноса между контейнерами/мониторами. Реализация и эксперименты не начаты.
