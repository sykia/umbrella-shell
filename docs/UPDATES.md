# ADR-001: обновления через WinSparkle и подписанный установщик

Статус: **архитектурное решение, runtime-интеграция не реализована**.
WinSparkle не скачан, не залинкован и не запускается. Реализованы только чистые
функции политики. Наличие `packageVerified=true` в тесте не означает проверки
подписи; к production-пути установки эти значения не подключены.

## Выбор

Использовать WinSparkle >= 0.9 с Ed25519 (EdDSA), стандартным appcast и Inno
Setup. Не писать свои криптографию, TLS, формат подписи или downloader.
Перед интеграцией закрепить конкретную проверенную версию и хеш зависимости,
проверить лицензию и актуальные security fixes.

GitHub Releases хранит подписанные installers. WinSparkle читает **appcast XML**,
а не GitHub Releases JSON: отдельный release-job должен сформировать ленту из
уже подписанных assets. Это ещё не сделано. SHA-256 рядом с файлом полезен для
диагностики, но не заменяет подпись: атакующий может заменить оба файла.

## Предполагаемый путь

1. Отложенная проверка appcast по HTTPS, ограничение частоты (например, сутки),
   jitter и backoff. Нет запроса при каждом запуске процесса и нет службы Windows.
2. WinSparkle выбирает совместимую более новую x64 версию; draft исключены,
   Stable не принимает prerelease. Отдельные HTTPS feeds Stable/Beta и отдельные
   установочные идентификаторы/каталоги до разрешения параллельной установки.
   В текущем релизном workflow допускаются только теги vMAJOR.MINOR.PATCH.
3. Фоновая загрузка средствами WinSparkle, его штатный progress/consent dialog.
   Интерфейс обновлений пока отсутствует; существующие Shell Bar и настройки
   не являются клиентом обновлений. Частичные загрузки не исполняются.
4. WinSparkle проверяет Ed25519 подпись полных байтов installer встроенным
   публичным ключом. Ошибка подписи, отсутствующий ключ, TLS error, неверный
   размер или отсутствие recovery-плана запрещают установку.
5. Дополнительная политика Authenticode через Windows WinVerifyTrust:
   проверка доверенной цепочки, timestamp/revocation policy и допустимого
   издателя. Сам факт «подписан любым сертификатом» недостаточен.
   До интеграции проверить точки расширения WinSparkle: если нельзя выполнить
   эту проверку **до запуска** без форка криптографии/скачивания, пересмотреть
   адаптер. Сейчас такая проверка в приложении отсутствует.
6. Только после явного согласия пользовательский installer, без elevation,
   с завершением приложения и без принудительного убийства Explorer.

Ed25519 private key хранится отдельно от исходников и сертификата Authenticode,
в защищённом release environment; публичный ключ вшивается в приложение.
Ключ из скачанного manifest не является доверенным. Ротация через релиз,
подписанный прежним ключом, с переходным окном; компрометация требует отдельного
плана отзыва. GitHub TLS и checksum не являются корнем доверия пакета.

## Транзакции и откат: блокирующее ограничение

**WinSparkle + обычная in-place установка Inno не дают гарантии атомарного
обновления и восстановления после выключения питания.** CloseApplications
помогает при занятых файлах, но не является транзакцией. Нельзя включать
автоустановку, считая эту задачу решённой.

Перед runtime-интеграцией требуется ADR-002 с выбором проверенного движка
транзакционной установки, предпочтительно Windows Installer (MSI/WiX) либо
MSIX, при необходимости под простым exe-bootstrapper. Проверить совместимость
с будущими возможностями shell и per-user установкой. Предпочтение Inno не
должно превращаться в самописный движок безопасности. MSI rollback относится
к ошибке установки, а не автоматически к падению приложения после установки.

Контракт recovery для следующего этапа:

- До изменения файлов сохранить предыдущий подписанный пакет и данные
  миграций; проверить свободное место, отсутствие конкурентной установки.
- Использовать staging/commit/rollback выбранного installer engine; не
  перезаписывать запущенные exe/DLL вручную и не скачивать код в process memory.
- Сохранить durable состояние установки вне заменяемых файлов. После restart
  engine обязан восстановить согласованный комплект файлов либо старую версию.
- Успех установки и успешный запуск shell — разные checkpoints. Health-check,
  ограниченное число запусков и opt-in rollback требуют отдельного supervisor
  и протокола. Не разрешать постоянный downgrade ниже security floor.
- Сохранять Explorer доступным весь процесс; при ошибке запускать стандартную
  оболочку. Не менять настройки схемой, которую предыдущая версия не прочтёт.
- Перед остановкой GUI/guard вернуть скрытые группы приложений и системную
  панель. Текущий shared-memory снимок групп не переживает смерть обоих процессов;
  его нельзя считать durable recovery или откатом установщика. ADR-002 должен
  отдельно определить поведение при отказе на этом этапе и проверить его в VM.

Автообновления остаются выключены до прохождения всей VM-матрицы:
подмена payload/feed, неизвестный издатель, истёкший сертификат с/без timestamp,
отмена, offline, disk full, locked DLL, параллельный setup, kill/reboot на каждой
стадии, повреждённый кэш, downgrade, падение новой версии и восстановление
настроек. Эти испытания пока не выполнены.
